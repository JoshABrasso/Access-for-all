1. Overview

The GM accessibility engine is a fully self-contained runtime preference system built to solve a problem that OS-level accessibility tools cannot solve in the real world: inconsistency. macOS VoiceOver and Zoom are excellent. ChromeOS accessibility is nearly non-functional. Linux kiosk and POS terminal environments have fractured or absent support. Corporate locked-down systems often have accessibility disabled entirely. The engine treats all of those environments identically, because it runs entirely inside the webpage.

Each user interaction writes a data-* attribute to <html> and, for numeric values, also writes a CSS custom property directly. CSS rules keyed to those attributes change the visual rendering immediately. No page reload. No class toggling. No framework dependency. No OS required.

The conjunction principle

Every axis works independently and in conjunction with every other axis. This is not incidental — it is the core design decision. A user with low vision, photosensitivity, and dyslexia does not need three separate tools. They need one engine that honours all three preferences simultaneously, as a single bespoke configuration. The engine never suppresses, softens, or overrides a combination because it looks unusual. If the user has chosen Dark mode + Yellow palette + Warm filter, that is an intentional, valid, and respected user decision.

The palette tool — what it actually does

A common misconception is that the palette tool is an accent colour picker. It is not. Activating a palette flattens the entire viewing surface. All backgrounds collapse to neutral greys (light mode) or near-blacks (dark mode). All shadows are suppressed. Images and hero art step back dramatically. The chosen colour then floods every chromatic role simultaneously — text, borders, accent, focus ring, and the full brand tonal scale. The result is a clean, single-colour reading environment where the chosen colour is the design.

When a palette is combined with high contrast (plus-3 or above), interactive elements escalate further: buttons transition from wireframe outlines to solid colour fills. At plus-4 and plus-5 all interactive surfaces — primary and secondary buttons, form inputs, card borders — fill solidly in the palette colour with contrasting text (e.g. Yellow fill, Black text). The visual hierarchy becomes entirely colour-driven with maximum separation between interactive and passive elements.

Persistence and boot

State is persisted in localStorage under the key "gm-accessibility-state" (version key: "gm-accessibility-version", current value: "5"). On every page load the engine reads stored state, normalises it, and applies it before the first paint — the page never flashes the default state first.

The engine exposes a public API at window.accessibilityEngine that site-ui.js and any page script can call to read, update, subscribe to, or reset state.

3. JS ↔ token chain

When a user changes a control, the sequence is:

  1. site-ui.js calls engine.updateState(newState)
  2. accessibility-engine.js normalises state → writes data-* attributes to <html>
  3. For numeric axes (fontScale, lineSpacing, etc.) the engine also writes CSS custom properties directly to :root — e.g. document.documentElement.style.setProperty("--gm-font-scale", value)
  4. CSS rules in themes/accessibility.css key to those attributes and tokens — e.g. html[data-appearance="dark"] { ... }
  5. Subscribers registered via engine.subscribe(fn) are notified
  6. State is written to localStorage

Numeric token writes (set on :root by the engine)

State key CSS property written Unit / calculation

letterSpacing--gm-letter-spacingvalue / 100 + em — max value 12 produces 0.12em, the WCAG 1.4.12 minimum letter-spacing
wordSpacing--gm-word-spacingvalue / 100em

5. Landmark axis — design rationale

Earlier engine versions had two separate boolean toggles: highlightControls (highlight buttons and inputs) and highlightRegions (highlight landmark regions). Real-world testing showed this combination caused issues:

  • Applying border to landmark elements caused layout shift
  • The two-control surface added visual noise in the engine panel
  • Highlighting form controls separately overlapped with focusBoost

The engine redesigns this as a single three-state axis:

Value Visual effect CSS technique
off No highlighting —
soft Subtle inset stripe inside each annotated region outline: var(--gm-landmark-stripe-width) solid color-mix(...) with a negative outline-offset
clear Dashed outer outline around each annotated region outline: 2px dashed color-mix(...) — stronger visibility without touching box model width

The engine's annotateRegions() function stamps data-accessibility-region on the shared shell and content containers it actually queries today: .site-header, .primary-nav, main, main section, main article, main aside, and .site-footer. CSS in themes/accessibility.css targets html[data-landmark="soft"] [data-accessibility-region] and html[data-landmark="clear"] [data-accessibility-region].

No pseudo-element labels. No border (which shifts layout). No JS class toggling.

6. localStorage structure

Two keys are written:

  • "gm-accessibility-state" — JSON object containing the full state snapshot
  • "gm-accessibility-version" — string "5"

On boot, if the stored version does not match "5", the stored state is discarded and defaults are used. This prevents stale state from a previous engine version causing incorrect rendering.

The storage layer is defensive by design. readStorage() and writeStorage() both sit inside try / catch, so private browsing restrictions, blocked storage, or quota errors do not crash the engine. The page simply falls back to the in-memory defaults.

Storage stepActual JS behaviourWhy it matters

Payload loadJSON.parse(stored) is merged with defaults then passed through normalizeState().Even valid JSON still has to pass the allowed-value rules.
Parse failureloadState() catches invalid JSON and returns a fresh copy of defaults.Corrupt storage cannot break boot.

7. State behaviour — independent, in conjunction, and without suppression

The engine models each axis completely independently, but every axis also stacks coherently with every other axis. This is not a convenience feature — it is the philosophical centre of the engine. Real users are not one-dimensional. A user may need dyslexia-friendly type and reduced motion and a warm filter because they are photosensitive and high contrast because they have low vision. The engine honours all four simultaneously as a single bespoke configuration.

The no-suppression principle

The engine never examines a combination of active axes and decides that the combination looks "wrong" or is "in conflict" and quietly overrides part of it. If a user selects Dark mode + Yellow palette + Warm filter, they have chosen all three of those things deliberately. The warm amber of the filter over the yellow palette in dark mode is not a mistake — it is exactly what the user intended. Suppressing or "correcting" any axis because of another is paternalistic and wrong.

This is a direct rejection of the accessibility tickbox mentality — the idea that there is one correct "dark mode" user, one correct "high contrast" user, one correct "dyslexia" user. There is no such thing. Each person's combination of preferences defines their personal interface. Every combination the engine can produce is valid.

How axes stay stable when stacked

The engine separates root state, token assignment, and component consumption into three distinct layers. That separation is what makes conjunction stable:

Axis pairing What happens Why it stays stable
appearance + palette Dark mode flips surfaces and text. Palette then remaps the accent family over the dark base. Theme tokens and palette tokens are distinct token families. They do not overwrite the same concern.
palette + contrast At plus-3: primary buttons become solid fills. At plus-4/5: all interactive elements fill with the palette colour and contrasting text (e.g. Yellow fill, Black text). The conjunction is modelled explicitly in variables.css. Specificity cascade ensures palette → contrast conjunction tokens win over individual axis tokens.
appearance + palette + contrast Dark + Yellow + Contrast plus-4 = near-black surfaces, yellow text and borders everywhere, solid yellow buttons with black text. Each axis writes into a separate token concern. The dark base flattens surfaces, the palette floods colour roles, the conjunction escalates fills. No axis can cancel another.
font + spacing + readingMode Typeface, text scale, letter spacing, word spacing, line height, and reading width all shift simultaneously. Each axis writes a separate runtime token. OpenDyslexic font automatically applies WCAG-compliant letter spacing (0.12em), word spacing (0.16em), and line height (1.65) as part of the font axis, not as a separate user step.
tint + filterStrength Tint selects the filter type. FilterStrength is a multiplier that independently increases or decreases the effect. The filter values are look-up table driven — each combination of tint × strength has its own token set. No runtime calculation.
tint + media The viewport filter shifts overall comfort. Media dimming dims and desaturates images independently. The viewport filter applies to .site-main/.site-header/.site-footer via CSS filter. Media dimming applies to img/video/picture elements separately. Two layers, no conflict.
appearance + tint + warm Dark + Warm is a valid deliberate choice — it was the user's intent. The engine executes it fully. No suppression. See no-suppression principle above.
contrast + transparency Higher contrast strengthens borders and surface separation. Transparency reduction removes blur and frosted effects. Contrast changes colour math. Transparency changes backdrop-filter and opacity behaviour. Separate axes, separate token concerns.
motion + depth Motion can reduce or stop while layered shadows still remain, unless depth is also changed. Motion controls transition-duration and animation-duration. Depth controls box-shadow tokens. One does not disable the other.
focus + links + landmark Focus rings, stronger link styling, and region visibility can all be active simultaneously. They affect distinct interactive signals: current target, link recognition, and page structure. No shared token path.
Design law: If a new control cannot operate independently and survive combination with every existing control without breaking either, it is not ready to join the engine. Controls that only work in isolation are half-built.

9. Implementation model — JS, tokens, and memory

The engine has three distinct layers of responsibility. Keeping them separate is the reason it can scale.

  1. Runtime state layer
    accessibility-engine.js owns defaults, allowed values, normalisation, localStorage versioning, read/write flow, and subscriber notifications.
  2. Presentation contract layer
    Root data-* attributes and runtime --gm-* properties form the contract that CSS reads. The engine writes state here, not into component classes.
  3. Consumption layer
    Components and layout CSS read the tokens. They should never need to know where the values came from, only that the token contract is valid.

Memory behaviour is intentionally simple: the active state lives in JavaScript memory, mirrors onto the root element, and is persisted to localStorage only as a normalised snapshot. On reload, the snapshot is re-read, re-normalised, and re-applied.

Phase What the engine does Where it writes
Boot Read stored version and state, reject stale or invalid values, resolve defaults. In-memory state object
Apply Write root attributes and runtime variables. <html> dataset and inline style properties
Notify Tell UI subscribers and speech subscribers that something changed. Subscriber callbacks
Persist Store the clean snapshot and version marker. localStorage

Actual boot sequence in accessibility-engine.js

1. Define defaults, allowed lists, speech state, and helper functions
2. loadState() → readStorage() → normalizeState()
3. annotateRegions() stamps data-accessibility-region on shared landmarks and sections
4. cacheSpeechVoices() hydrates browser voice candidates when available
5. applyState(state) writes dataset values, runtime CSS props, any optional logo variants, and form values
6. Runtime listeners attach for guide movement, talkback, speech, resize, visibility, and theme sync
7. window.accessibilityEngine is exposed for site-ui.js and any other page consumer

10. How to add a new engine control

Adding a new accessibility axis is a four-step process:

  1. Add to defaults in accessibility-engine.js
    myAxis: "default"
  2. Add to normalizeState() in accessibility-engine.js
    myAxis: normalizeChoice(nextState.myAxis, allowedMyAxisValues, defaults.myAxis)
  3. Write the data attribute and/or CSS token in applyState()
    root.dataset.myAxis = state.myAxis;
    or for numeric: root.style.setProperty("--gm-my-token", computedValue);
  4. Add the CSS rule in themes/accessibility.css
    html[data-my-axis="value"] { /* rule */ }
  5. Add the form field in each page's engine modal HTML
    <label class="control-stack"><span>Label</span><select name="myAxis">...</select></label>
  6. Add to acMobileBranches in site-ui.js
    Add "myAxis" to the appropriate branch's fields array.
  7. Add to collectFormState() in site-ui.js
    myAxis: getFieldValue("myAxis", currentState.myAxis)
Never add new CSS rules to variables.css or any base/layout file. New engine state rules belong only in themes/accessibility.css.

12. Talkback / read-aloud

Talkback uses the browser's SpeechSynthesis API. It is not a screen reader — it is an on-demand reading layer for users who want spoken support without enabling full assistive technology.

  • Hover / focus talkback — reads the element under the pointer or the focused element, depending on talkbackMode ("hover", "focus", or "both").
  • Read-aloud — reads the full page sequentially. Controlled via [data-speech-play], [data-speech-pause], [data-speech-stop] buttons.
  • Scoped talkback — activateScopedTalkback(element) restricts hover/focus reading to a specific DOM subtree. Used in the engine modal so talkback only reads the panel while it is open.

Elements can have a data-speech-description attribute to provide an alternative spoken label — used on images and complex interactive elements.

Voice and queue model

Voice selection is scored rather than guessed. The engine caches browser voices, checks preferred languages from the document and browser, rewards signals such as default, localService, natural, and neural, and penalises lower-quality markers such as espeak. The highest-scoring voice is then assigned in configureUtterance().

Live talkback and full-page reading are separate flows. speakLiveTarget() describes one current element at a time, while page reading builds a speechQueue from headings, paragraphs, list items, blockquotes, figcaptions, legends, engine notes, and control descriptions, then advances through the queue with speakNextBlock() until the session ends.

Speech label precedence

For live target speech, the runtime resolves a label chain in order and stops at the first useful result instead of blindly reading raw text content.

2data-speech-description / aria-labelUsed for custom wording or non-visible descriptive copy.
3aria-labelledby and linked label textResolves associated labels for real form fields and grouped controls.
4Image description chainFor images: data-speech-description, aria-description, data-image-description, alt, then figcaption.
5Placeholder / current field value / textContentFallbacks for plain text fields and ordinary content nodes.

13. Consent system

site-ui.js includes a lightweight consent banner and modal. Storage keys:

  • "gm-consent-state" — JSON: { analytics: bool, marketing: bool }
  • "gm-consent-version" — "1"

The banner and modal HTML are injected by JS. You do not need to add them to pages manually. The footer button with data-consent-manage-open opens the modal for users who want to change their choices later.

The consent system does not set any cookies itself. Wire your analytics or marketing scripts to check consent state before executing.

14. Build and integration rules

These rules apply to every file in this project, without exception:

Rule 1 — No hard-coded colours in components Every colour value must come from a CSS custom property token. Never write hex, rgb(), or hsl() in component files. Use color-mix() for computed values.
Rule 2 — master.css imports only master.css must contain nothing but @import statements. No visual rules. Load order is enforced by the import sequence.
Rule 3 — Variables.css declares, accessibility.css overrides All token declarations live in base/variables.css. All engine state overrides live in themes/accessibility.css. No engine state rules in any other file.
Rule 4 — Keep the starter neutral The GM is a reusable starting point. Keep reference pages and demo copy generic, and do not let product-specific branding or project-specific content become part of the shared engine baseline.
Rule 5 — CSS namespace Engine tokens use the --gm- prefix. Avoid introducing one-off prefixes that tie shared engine styles to a single page or build.
Rule 6 — No layout shift from engine controls Engine state changes must not shift content. Use outline not border when adding visual indicators to existing elements. The GM landmark axis follows this by using outlines and outline offsets rather than adding border width or padding.
Rule 7 — No direct DOM manipulation of state attributes State attributes on <html> must only be written by accessibility-engine.js via applyState(). No other script should write data-appearance, data-palette, etc.
Rule 8 — The engine modal must not receive the visual filter The --site-visual-filter is applied to the site shell. The engine modal must be outside the site shell or otherwise excluded, so filter changes don't distort the panel the user is currently adjusting.
Rule 9 — Modular CSS, never a monolith CSS files must not be merged. Each file has a single, named responsibility. Source order is the cascade — do not fight it with !important.
Rule 10 — Deletable pages are clearly marked demo.html and engine.html carry a visible optional-use banner, a noindex, nofollow robots tag, and a comment block at the top of the file. index.html is the only page that ships by default.
Rule 11 — The engine never suppresses a user combination No engine code, CSS rule, or token conjunction block may detect an axis combination and reduce, override, or silently soften another axis because of it. Dark + Yellow + Warm is a user decision, not an error state. Every combination the engine can produce is valid and intentional. Suppression is paternalistic and belongs in no accessibility tool.
Rule 12 — OS independence is a first-class requirement The engine must function identically on macOS, Windows, ChromeOS, Linux kiosks, POS terminals, and corporate locked-down environments. Any feature that requires an OS-level accessibility API to function is not complete. Design for the user whose OS gives them nothing.
